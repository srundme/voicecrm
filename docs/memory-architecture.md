# VoiceCRM — Cross-Call Memory Architecture

> **How Dhivya remembers every customer across every call**

---

## The Core Problem

Standard AI voice agents have **no memory**. Each call starts completely fresh.
A customer who said *"call me tomorrow at 2pm"* on Monday gets the same cold opening on Tuesday.
This destroys trust and makes automation feel robotic.

VoiceCRM solves this with a **persistent memory loop** built entirely on top of the database.

```

┌──────────────────────────────────────────────────────────────┐
│                        call_logs                             │
│                                                              │
│  id          │ UUID                                          │

                        follow_ups
```

## How Memory Is Built (buildCallContext)

```
buildCallContext(phone)
        │
        ├─► Normalise phone → 10-digit Indian format
        │
        ├─► Query: leads WHERE phone = ?
        │           ↓
        │   [Name, City, Gender, Insurance Type, Stage]
        │
        ├─► Query: call_logs WHERE lead_id = ? ORDER BY created_at DESC LIMIT 1
        │           ↓
        │   [Last call summary, execution_id, drop_detected, created_at]
        │
        ├─► Query: follow_ups WHERE lead_id = ? AND status = PENDING
        │          AND type = CALLBACK_REQUESTED
        │           ↓
        │   [Pending callback? notes? scheduled_at?]
        │
        ├─► Query: policies WHERE lead_id = ? ORDER BY created_at DESC LIMIT 1
        │           ↓
        │   [Policy number, renewal date, insurer]
        │
        └─► Decision tree:
                │
                ├─ No lead found?          → call_type: inbound_new   (blank context)
                ├─ No prior calls?         → call_type: new            (form context only)
                ├─ Drop within 15 min?     → call_type: drop_retry     (summary as context)
                ├─ Pending callback?       → call_type: callback       (callback_reason + summary)
                └─ Known, no pending?      → call_type: inbound_known  (summary + policy)
```

## What Makes This Unique

| Feature | Standard Voice Bot | VoiceCRM |
|---|---|---|
| Memory across calls | ❌ Resets every call | ✅ DB-persisted summary |
| Callback scheduling | ❌ Manual | ✅ Auto-detected from transcript |
| Opening line | ❌ Same every time | ✅ Dynamic per call context |
| Drop recovery | ❌ Same cold opening | ✅ Apologetic + continues from summary |
| Inbound context | ❌ Treats caller as unknown | ✅ Full history injected |
| Memory creation | ❌ N/A | ✅ AI extraction after every call |

## Technical Summary (For Judges)

**Memory is stored** as an AI-generated text summary in `call_logs.summary`, produced by Bolna's post-call extraction (GPT-4.1 Mini) after every call ends.

**Memory is retrieved** by `buildCallContext()` — a function that runs before every single outbound call and every inbound call, querying the database for the most recent call log for that phone number.

**Memory is injected** by passing the summary as `{context}` inside the `user_data` object sent to Bolna's `/call` API. Bolna makes this available as a template variable in Dhivya's system prompt.

**Memory is used** by the system prompt instruction: `[MEMORY FROM LAST CALL — read this before speaking]: {context} — Do NOT restart the conversation. Continue from where the last call ended.`

**Cross-call context for callbacks** is even richer: the `callback_reason` variable combines both the follow-up notes ("Customer requested callback in 2 hour(s)") AND the previous call summary, giving Dhivya full situational awareness before she even says hello.

The entire system requires **zero manual data entry** — memory is created automatically from conversations, stored in Postgres, and re-injected on every subsequent interaction.
